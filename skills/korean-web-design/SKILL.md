# 한국어 웹 화면 설계

1. **사람과 과제부터 정한다.** 기존 제품 설명·기능·대상·브랜드·기술 스택을 확인한다. 샘플에 등장하는 직업이나 장면으로 전체 고객을 규정하지 않는다. 진단 요청에는 관찰과 근거를, 시안 요청에는 비교 가능한 화면을, 구현 요청에는 동작하는 변경을 제공한다.
2. **첫 화면의 역할을 정한다.** 랜딩에서는 방문자가 얻게 될 결과를 실제 콘텐츠나 작동하는 샘플로 보여 준다. 제품 내부에서는 한 가지 과제를 선택해 진입부터 완료·취소·복귀까지 따라간다. 권한·결제·외부 전송 등 중요한 조건은 행동을 결정하는 위치에서 설명한다.
3. **레퍼런스에서 결정 하나를 가져온다.** 한국어 제품 UI는 [당근 SEED 활용 가이드](references/seed-design.md)에서 과제에 맞는 조판·문구·컴포넌트·모바일 패턴을 먼저 확인한다. 한국어로 운영되는 서비스의 글자·여백·정보량, 비슷한 과제를 다루는 서비스의 흐름을 본다. 참고한 화면 링크와 가져올 이유를 붙인다. 컴포넌트나 도구가 필요할 때 [자료 선택표](references/toolkit.md)를 사용한다.
4. **실제 문장으로 설계한다.** 제목, 본문, 버튼, 캡션의 위계를 정하고 가장 짧은 값과 긴 값을 모두 넣는다. 제목이 답답하거나 마지막 줄이 어색하면 강제 개행·글꼴·행간·자간을 각각 바꿔 원인을 찾는다. [한국어 조판과 문구](references/korean-type.md)
5. **범위에 맞게 비교한다.** 방향이 열린 작업은 같은 콘텐츠·기능으로 구도가 다른 안을 비교하고 추천 이유를 제시한다. 이미 선택된 디자인이나 국소 수정은 해당 과제에 집중한다. 기존 토큰·컴포넌트를 활용하고, 프로젝트의 어투와 사용자층에 맞춰 쓴다.
6. **렌더와 행동을 확인한다.** 모바일과 데스크톱에서 실제 화면을 열어 핵심 과제를 수행한다. 글자 확대, 키보드, 긴 한국어, 빈 데이터·오류 등 관련 상태를 본다. 결과에는 확인한 환경과 미확인 환경을 구분한다. 사용자가 이해하는지에 관한 결론은 실제 사용 관찰로 확인한다.

시안 비교와 초안 인수에는 [디자인 요청 프롬프트](references/design-prompts.md)를 활용한다. 공개 자료에는 범용 판단 기준만 담고 프로젝트 고유 자료는 원래 작업 공간에 보관한다.
